# プロジェクトローカル skill

[English](project-local-skills.md)

**ゲートは skill 自身の `SKILL.md` に、そのチェックアウトが今実行できるプロダクトのコマンドとして書きます。**
進行は、そのファイルの中のフェンスされたシェルコマンドが終了コード 0 になることです。
この skill に従う人は、リポジトリ自身の道具を使います。
ファイルに従うために、headsign のプログラムは要りません。

三つの skill がそのファイルを書き、または直し、そこで止まります。
ファイルが述べる日々の仕事を、これらの skill が運転し続けることはありません。
[`optimize`](../plugin/skills/optimize/SKILL.md) は別の skill です。
終えた headsign の run を評価します。
skill ファイルは編集しません。

書くファイルの既定の置き場は `.agents/skills/<name>/SKILL.md` です。
リポジトリが貢献者向け skill の置き場を別に書いていれば、ファイルはそこへ置きます。
パッケージが下流の利用者へ公開するディレクトリには書きません。
そのディレクトリが貢献者向け skill の置き場だと、あなたが言った場合は別です。

短い版は [README](../README.ja.md#プロジェクトローカル-skill) にあります。
エージェントが従う手順は、下の各見出しが指す skill の入口です。
入口は、`references/` の中で開くファイルを一つ名指しします。
このページは、人が読むための説明です。

## どの skill か

| Skill | 選ぶとき | 得られるもの |
|---|---|---|
| [`create-skill-workflow`](../plugin/skills/create-skill-workflow/SKILL.md) | リポジトリをエージェント作業の場にするとき、または繰り返す CI の失敗をローカル skill に受けさせたいとき。写す対象の workflow の検査は無い | このチェックアウトが実行できるコマンドを調査して発明した、新しいローカル skill |
| [`project-skill`](../plugin/skills/project-skill/SKILL.md) | あなたが名指しした workflow ファイルに検査の `run` 文字列があるとき、または写すべきコマンドをあなたが名指ししたとき | 同じ形のファイル。ゲートはそれらの `run` 文字列 |
| [`optimize-skill-workflow`](../plugin/skills/optimize-skill-workflow/SKILL.md) | skill に既に名前があり、中身がおかしいとき。目的と矛盾するランタイム、チェックアウトが実行できない受け入れコマンド、同一セッションの二つの役だけのレビュー | その skill への小さな差分 |

`create-skill-workflow` は発明します。
`project-skill` は写します。
`optimize-skill-workflow` は、あなたが名指しした skill を改訂します。
skill ファイルを直してほしい依頼は `optimize-skill-workflow` です。
既に終えた run を評価してほしい依頼は `optimize` です。

headsign の workflow を設計するのは [`design-workflow`](../plugin/skills/design-workflow/SKILL.md) です。
その run を運転するのは [`workflow`](../plugin/skills/workflow/SKILL.md) です。

## create-skill-workflow

ローカル skill を発明する必要があるときに、この skill を使います。
リポジトリに workflow ファイルがあることもあります。
その検査を写すのはもう一つの skill の仕事であり、こちらはそう言って止まります。

エージェントは書く前に調査します。
コマンドは、リポジトリが実際に綴っているとおりに記録します。
テスト、lint、型検査、ビルド、アーキテクチャ検査、差分や方針の検査、エンドツーエンドや画面の検査、そしてリポジトリが持っているときのプロパティテストやミューテーションです。
一つのコマンドになりうる散文の規則、最近の変更がどのくらいの大きさか、エージェントが既に持っているものも見ます。
短い一覧をあなたに見せます。

必須の結果を変える答え、または自分では選べない制約が欠けているときに尋ねます。
一度に一つです。
尋ねる前にリポジトリから答えを出し、その説明が答えになった質問は飛ばします。
決める欠落は、Done の意味、構造のゲートがあるか、仕事が触れてよいパス、独立したレビューを実際にどう作るか、skill が自分をいつ振り返るか、そしてランタイムです。
ランタイムの既定は、ローカル skill がリポジトリ自身のコマンドで回ることです。

無いとあなたが言った道具は、目的と候補としてツールメニューに残します。
ゲートにはしません。
skill はファイルを書き、AGENTS.md に一行のポインタを足す前に尋ね、最初の仕事として試せる目的を一つ名指しし、ゲートに置いたコマンドを一つずつスモークテストします。
このチェックアウトが実行できるところまで確認します。
足りない依存は、必須のゲートのまま残しません。

手順は [references/procedure.md](../plugin/skills/create-skill-workflow/references/procedure.md) です。

## project-skill

ゲートが既にシェルコマンドとしてあり、チームが単独で従える skill に置くのが仕事であるときに、この skill を使います。

あなたが名指しした既存の workflow ファイルがあるとき、各 `gate.checks` の `run` 文字列を一つのフェンスへ写します。
ファイルに現れる順で、`run` 一つが一行です。
コマンドは書かれているとおりに写します。
`&&` や `||` を含む `run` は一行のままです。
フェンスの中のコマンドは、すべて終了コード 0 でなければなりません。
`on_pass` は見出しの行き先です。
`on_fail` はフェンスの下の一行です。
0 以外の終了はそこへ戻ります。
`when:` プローブを持つ `on_pass` は、一つのフェンスのままです。
エージェントはその行を丸ごと実行します。
`timeout:` は、その行の脇に置く予算の文です。

フェンスの上では、ゲートが読むものを作る作業を一行か二行で名指しします。
その作業は説明です。
ゲートはコマンドです。
フェンスの下では、エージェントが実際に見た stderr を、直し方と一緒に引用してよいです。
メッセージを知るためにチェッカーを読みます。
文言を知るためだけに、書き込みやコミットやチケットの取得をするコマンドは実行しません。
メッセージを発明することもありません。

workflow ファイルが無いときは、あなたが名指ししたコマンド、または指したスクリプトだけを使い、あなたの検査としてラベルします。
発見、方針、リポジトリから発明しなければならない skill は `create-skill-workflow` です。

生成した skill のゲートは、その `SKILL.md` に置きます。
その skill を運転するエージェントは、シェルをそこで見ます。
書いたあと、各 `run` 文字列はゲートのフェンスの中に一度だけ現れます。

仕事に単一の所有者が要るとき、**When to use** には次の文が入ります。
二つの所有ループを同時に回さない、という文です。
判断には薄い所有ファイルを使います。
その文は二つ目のループを断ります。
ゲートではありません。
ゲート自体は、プロダクトのコマンドのままです。

この skill はコマンドを写します。
フェーズは設計せず、run も開始しません。
コマンドを発見するために、プログラムをインストールすることもありません。

写したゲートの規則は [references/gates.md](../plugin/skills/project-skill/references/gates.md) です。
節の順は [references/shape.md](../plugin/skills/project-skill/references/shape.md) です。

## optimize-skill-workflow

既にある skill を直したいときに、この skill を使います。
名前を挙げるか、パスを渡すか、直前に話していたものを指します。
エージェントはそのファイルを見つけ、読み、短い診断を渡します。
あなたは変更を一つか、二つか、三つまで合意します。
エージェントは合意したものだけを適用して止まります。
有用な方法はそのままでよいです。
選ばなかった診断項目は、一覧に残し、触れません。

診断が先に見るのは、いつ使うかを述べていない description、厚すぎて道具を選べない手順、エージェントの報告でしかない Done、チェックアウトと食い違うコマンドやパス、消えたのに Gates や受け入れ文に残っているチェッカー名、そして目的と矛盾するランタイム依存です。
最後のものは、リポジトリ自身のコマンドで回ると言いながら、ゲートにオーケストレーターの状態を要求している skill です。
同一セッションで二つの役を演じるだけの独立レビュー、オーケストレーターの状態を読まないと決まらない所有、共有 skill に書き込まれた一つのアシスタントのチャンネルや個人名、ローカル skill の形が要求する節の欠落、同じ方針の二重保持も見ます。
振り返りがゲートの無視を示す前に、Self-improve が hook による強制を提案していることも見ます。

矛盾するランタイムの修理は、オーケストレーターの状態を必須の経路から外します。
その場所には、薄い所有ファイルと実在するキューが入ります。
古くなった受け入れの修理は、消えたコマンドを削除し、チケットの文と Gates が同じ生きたコマンドを名指しするようにします。
どちらの修理のあとでも、ゲートに残ったコマンドはすべてスモークテストします。
足りない依存は、必須のままにしません。

インストール済みのプラグインや、管理されたカタログのコピーは読み取り専用です。
変更は、リポジトリへのフォーク、またはホストが書き込みを許す skill の置き場へのフォークです。
インストール済みのファイルはそのままです。

手順は [references/procedure.md](../plugin/skills/optimize-skill-workflow/references/procedure.md) です。

## ファイルが備えるもの

二つの執筆 skill は、一つの `SKILL.md` を書きます。
ゲートはそのファイルに、次の順で置きます。

1. **When to use。** 二つ目の所有ループを断る文をここに置いてよいです。ゲートではありません。判断には薄い所有ファイルを使います。
2. **Goals。** 三つの結果です。ゲートを言い換えた手順の一覧は置きません。
3. **Gates。** 進行一つにつき見出し一つです。フェンスがゲートです。
4. **Tool menu。** ゲートが読むものを作る助けになるコマンドです。それ自体はゲートではありません。
5. **Constraints。** 終了コード 0 を無理に取るためにエージェントがやってはならないことです。焦点と、契約へのポインタを含みます。
6. **Evidence。** 仕事が終わったときに残る検査結果、満たせなかった基準、停止の理由です。
7. **Self-improve。** 振り返りです。シェルのゲートではありません。

**Done** は、最後のゲートが通ったときに真であることです。
写した workflow のコミットゲートがローカルコミットを求めるなら、それも含みます。
push は、あなたが求めたときに行います。
**Impossible** は、受け入れが守るべき契約と矛盾すること、または検査を弱めなければ通れないゲートです。
**Needs human** は、権限や情報が無いこと、または仕事を発明しなければ通れない検査です。

フロントマターの `description` は、いつその skill を使うかと、Gates のコマンドの終了コード 0 だけが進行であることを述べます。

### ゲート

ゲートは、このチェックアウトが今実行できるコマンドです。
プロダクトのコマンドを優先します。
テストスイート、リンタ、型検査、ビルド、リポジトリが既に綴っているアーキテクチャ検査です。
進行一つにつきフェンスは一つです。
フェンスの中の各行は、終了コード 0 でなければなりません。

形の見本です。コマンドは仮のものです。
実際のファイルは、チェックアウトが綴っているリポジトリのコマンドを、そのまま使います。

````markdown
### Tests pass → review

Make the change the ticket describes. That work is not the gate.

```sh
npm test
```

Exit 0 advances to review. Any other exit returns to this work.
````

消えたバイナリ、別の道具に属していたサブコマンド、まだ誰もインストールしていない依存は、Gates に現れません。
ミューテーションや他の重い検査は、あなたがゲートにすると決めた場合を除き、プロダクトのゲートから外します。
skill は、それらをいつ実行するかを書きます。
常設の方針であるコマンドや、CI が実行するコマンドでも、どのゲートも名指ししていないものはツールメニューに置き、ゲートではないと書きます。
同じコマンドを、通さなければならないものの第二の一覧として繰り返すことはありません。

### キュー

キューは、既に存在する CLI です。
その CLI がインストールされているときの通常の例は `bd` です。
課題追跡の CLI もキューです。
リポジトリが既に持つ薄いマニフェストもキューです。
skill はキューを新たに実装しません。
どれも無いときは、その旨を書き、仕事を動かすことは **Needs human** です。

### 所有

仕事に単一の所有者が要るとき、git 管理外の薄いファイルで足ります。
`loop.json` がその例です。
生成した skill は、そのファイルを読んで、所有のループを一つに保ちます。
`optimize-skill-workflow` は、薄いファイルで足りる skill がオーケストレーターの状態の読み取りを必須にしていることを、直すべき欠陥とみなします。

### 受け入れの文

チケットや指摘の文は、Gates かツールメニューが既に名指ししているコマンドを使います。
チェックアウトが実行できないチェッカー名は除きます。
受け入れの文を同期した改訂のあと、ゲートに残るコマンドは、このチェックアウトが実行できるものです。
消えたコマンドを文に残したまま、同期が終わったと呼ぶ編集は失敗です。

### 独立したレビュー

Constraints に「作者は自分の変更を承認しない」と書くだけでは、レビューになりません。
skill は次のうち少なくとも一つを要求します。
複数でもかまいません。
どれにするかは、あなたが合意します。

- 別のセッション、または別のエージェントが判定を書きます。これを優先します。
- コマンドが判定ファイルを検査します。種類、リビジョン、チケット、ベースです。人の理由は空でない Markdown です。これらの検査は必須です。
- 同一セッションで役を演じるしかないときは、その限界を Constraints に書き、Self-improve が見張ります。

`project-skill` が独立したレビュアーを求めるフェーズを写すとき、作業の行は判定ファイルを名指しし、変更の作者が承認を書かないと述べます。
却下、古い、空の判定は、チェッカー自身のメッセージがそう言ってから、作り手へ戻る 0 以外の終了です。

### Self-improve

ローカル skill は、完了時、同じゲートが二度失敗したあと、またはその両方で振り返ります。
いつにするかは、決めたとおりです。
記録の 1 行目は `NO_CHANGE`、`APPLIED`、`PROPOSED`、`DEFERRED` のちょうど一つです。
空でない説明が続きます。
一度だけです。
これは、終えた run に対して [`optimize`](../plugin/skills/optimize/SKILL.md) が使う四語と同じです。
ここでは、この skill、検査コマンド、または人が受け入れる提案を振り返る記録です。
方法が良くなったことの証明ではありません。

`APPLIED` は、現在の方針の内側での変更と、それをどう検証したかです。
`PROPOSED` は、人が要る変更です。
対象は AGENTS.md、契約、CI であり、次の一歩を名指しします。
振り返りが、同じゲートが無視され続けていることを示しているときは、`PROPOSED` が hook による強制を名指しします。
その強制は、ゲートが通るまでターンを止める host の hook です。
headsign も、別の host の hook も、この提案の一種です。
`DEFERRED` は見送りと、その理由です。
記録は、リポジトリがこの種のメモを既に置いている場所へ置きます。
git 管理外の作業ログか、変更説明の短い節です。

## ゲートが無視され続けるとき

ローカル skill は、その文章と、プロダクトのコマンドと、存在するキューで回ります。
調査は、skill を書く前に機械的な信号を列挙してよいです。
その一回の成果物は、ローカル skill です。

繰り返す CI の失敗は、ゲートや検査を直す理由です。
hook による強制を提案するのは、振り返りが、エージェントがそれらのゲートを無視し続けていることを示しているときです。
Self-improve は `PROPOSED` を記録し、ゲートが通るまでターンを止める host の hook を名指しします。
headsign はその host の一つです。
別の host の hook も同じ提案です。
記録は次の一歩を名指しします。
これらの skill は、頼まれない限り、同じ一回の中でその hook を入れません。

`optimize-skill-workflow` は、リポジトリ自身のコマンドで回る skill の修理として、オーケストレーターの読み取りを必須には加えません。

## skill を単独で使う

**ファイルを書く。** 三つの skill は指示です。
ローカル skill を書き、または直し、そこで止まります。

プラグインを入れているなら、skill の名前を指定します。
入れていないなら、[ワークフローリファレンス](workflow-reference.ja.md#プラグインなしで使う) が `workflow` を入れるのと同じ形で、その skill だけを入れます。

```
gh skill install meganemura/headsign create-skill-workflow
```

同じコマンドの名前を `project-skill` または `optimize-skill-workflow` にすれば、その skill が入ります。
上にリンクした `SKILL.md` をエージェントに指し、その入口に従うよう言っても同じです。
入口が名指しした `references/` のファイルを一つ開き、`.agents/skills/<name>/SKILL.md` を書きまたは直し、そこで止まります。

**ファイルに従う。** そのあとの仕事は、ローカル skill を読みます。
エージェントはゲートの上に書かれた作業をし、フェンスのコマンドを実行し、終了コード 0 を進行とみなします。
仕事に単一の所有者が要るとき、When to use は、二つの所有ループを同時に回さない、と書きます。
判断には薄い所有ファイルを使います。
その文は拒否であり、ゲートではありません。
Node が要るのは、プロダクト自身のコマンドが Node を要るときだけです。

headsign を一度もインストールしないチームでも、ローカル skill をリポジトリに置き、各エージェントにそれを指させられます。
hook による強制は、振り返りがゲートの無視が続いていることを示してから記録する、あとの提案です。
